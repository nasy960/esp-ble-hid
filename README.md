# USB → BLE 키보드·마우스 스위치

ESP32-S3의 USB Host로 허브에 연결한 키보드·마우스 리시버를 읽고,
두 BLE 연결 중 선택한 PC에만 HID 입력을 보냅니다.

## 연결

- PC → 보드 COM/UART 포트: 전원, 업로드, 115200 baud 로그·명령 입력
- 보드 USB/OTG 포트 → 외부 전원 허브의 upstream 포트
- 허브 → 키보드 리시버, Logitech Lift 리시버

Lift는 USB 리시버에 계속 연결합니다. PC에서 페어링할 대상은 Lift가 아니라
보드가 광고하는 **ESP USB Switch**입니다. 두 PC에는 BLE HID 지원이 필요합니다.
Bluetooth Classic과 부팅 전 BIOS 입력은 지원 범위에 포함하지 않습니다.

## 빌드·업로드

펌웨어 프로젝트는 `test/`에 있습니다. ESP-IDF 터미널에서 저장소 최상위로
이동한 뒤 실행합니다.

```sh
idf.py -C test build
idf.py -C test -p PORT flash monitor
```

PORT는 COM/UART 쪽 시리얼 포트입니다. 처음 빌드할 때 USB Host 의존성이
다운로드됩니다. 기존 NVS를 자동으로 지우지 않으므로 일반 업로드는
페어링 정보를 보존합니다.

## B 노트북의 Windows / Ubuntu 자동 키 선택

장치 표시 이름은 **`ESP USB Switch`**입니다. B 노트북의 공개 Bluetooth 주소
`AC:19:8E:C7:78:23`에 대해 Windows/Ubuntu 본딩 키를 별도로 보관합니다.
기존 페어링으로 재접속할 때는 마지막 인증 성공 키를 먼저 사용하고, 인증 실패·키 없음·
MIC 오류가 확인되면 다음 재접속에서 아직 실패하지 않은 다른 저장 키를 시도합니다.
일반적인 원격 연결 종료·타임아웃·리소스 부족으로는 후보를 바꾸지 않습니다.
두 후보가 실패하면 키 시도를 중단하며 `os retry`로 실패 기록만 초기화할 수 있습니다.
PC가 실패 후 자동으로 다시 접속하지 않으면 PC의 Bluetooth 설정에서 연결을 누릅니다.

이름 조회는 재접속 인증 성공 후 진단용으로 수행하며, 응답이 없어도 정상 연결을 유지합니다.
신규/재등록(`pair b`)에만 이름 `jsy`(Ubuntu), `DESKTOP-36CBTO9`(Windows)를 사용해 저장할
영역을 결정합니다. 이 등록 경로에서는 이름 조회가 필요합니다.
**두 OS를 이미 등록했다면 이번 업데이트 후 `forget`이나 재페어링은 필요 없습니다.**
아래 최초 등록 절차는 OS별 키를 아직 등록하지 않은 경우에만 적용합니다.

업데이트 후 최초 등록:

1. 보드에 새 펌웨어를 올립니다. 기존 보드 주소와 A의 저장 정보는 유지됩니다.
   PC에 이전 이름이 캐시되어 보일 수 있습니다. A가 계속 연결되면 다시 등록할 필요 없습니다.
2. COM에서 **`forget b`를 한 번만** 실행해 B의 기존 등록을 정리합니다.
3. B의 Windows 설정에서 이전 보드 항목을 제거하고, COM `pair b` 후
   `ESP USB Switch`를 새로 페어링합니다. `registration complete`까지 기다립니다.
4. B를 Ubuntu로 부팅하고 Ubuntu에서도 이전 보드 항목을 제거합니다.
   **`forget b`는 다시 실행하지 않고**, `pair b` 후 같은 보드를 새로 페어링합니다.
5. 이후 OS를 바꿀 때는 저장된 연결을 사용합니다. `pair b`나 OS 전환 단축키는 필요 없습니다.
   OS가 자동 접속하지 않는 경우 해당 OS의 Bluetooth 설정에서 연결을 누릅니다.

B 키 선택은 보드를 재부팅하거나 A 연결을 종료하지 않습니다. `forget b`는 현재 저장
영역의 **두 OS 키 모두** 삭제합니다. 다른 OS를 추가하거나 다시 등록할 때 사용하지 마세요.
등록 창을 열지 않으면 새로운 키로 덮어쓸 수 없습니다. 해당 노트북의 공개 주소와 실측
이름에 한정한 구현이며, 컴퓨터 이름 변경·다른 Bluetooth 어댑터·RPA 연결은 별도 대응이 필요합니다.

기존 `os ubuntu` / `os windows` 및 Ctrl+Alt+F10/F11은 과거 보드 전체 저장 영역을
수동 전환하는 기능으로 남아 있습니다. 이 자동 선택 절차에서는 사용하지 않습니다.
수동 전환하면 주소와 A/B 저장 영역이 바뀌고 재부팅되므로 새 등록이 필요할 수 있습니다.

## PC 등록 (처음 한 번, 각 OS에서)

시리얼 모니터 없이 **보드의 USB 허브에 연결된 키보드**로 등록 모드를 열 수 있습니다.
좌우 Ctrl/Alt/Shift 모두 사용할 수 있습니다.

| 키 조합 | 동작 |
| --- | --- |
| **Ctrl+Alt+Shift+←** | PC A 등록 모드 (120초) |
| **Ctrl+Alt+Shift+→** | PC B 등록 모드 (120초) |
| **Ctrl+Alt+Shift+↓** | 등록 모드 취소 (저장 목록 유지) |
| **Ctrl+Alt+Shift+Backspace**, 3초 유지 | A/B의 모든 등록 목록·본딩 키 삭제 |

1. A 등록 단축키를 누르면 RGB LED가 **초록으로 빠르게 점멸**합니다.
2. PC A의 Bluetooth 설정에서 **ESP USB Switch**를 추가합니다.
3. 본딩·암호화·HID 구독이 완료되면 등록 모드가 자동 종료되고 PC A가 선택됩니다.
4. B 등록 단축키를 누르고 PC B에서도 같은 방법으로 등록합니다. 등록 중에는
   **파랑으로 빠르게 점멸**하며 완료 후 PC B가 선택됩니다.

초기화는 등록 모드 취소와 다릅니다. 초기화 단축키를 3초 전에 놓거나 USB 키보드를
분리하면 취소됩니다. 3초 유지하면 BLE 연결을 끊고 현재 프로필의 A/B 등록을 삭제합니다.
계속 누르고 있어도 한 번만 실행되며, 초기화 후 자동으로 등록 모드를 열지는 않습니다.
다시 등록할 때 각 OS의 Bluetooth 설정에서도 현재 프로필의 ESP Switch 항목을 제거한 뒤
A/B 등록 단축키를 사용하세요.

같은 단축키를 계속 누르고 있어도 등록 시간이 반복 연장되지는 않습니다.
화살표를 놓았다 다시 눌러야 재실행됩니다. 단축키의 화살표 입력은 PC에 전달하지
않으며, 인식 당시 누르고 있던 키는 한 번 놓은 뒤 다시 눌러야 전달됩니다.
두 방향키를 동시에 누르면 어느 쪽에도 등록하지 않습니다.

등록 대상 슬롯이 이미 연결돼 있으면 그 연결을 끊어 새 기기가 연결할 자리를 만듭니다.
**기존 저장 목록과 본딩 키는 지우지 않습니다.** 기존 PC가 자동 재연결하여 슬롯을
차지하면, 해당 PC의 Bluetooth 연결을 잠시 해제하고 새 기기를 등록하세요.

기존 COM 명령도 그대로 사용할 수 있습니다. 시리얼 모니터에서 `pair a`, `pair b`,
`pair off` 입력 후 Enter를 누르면 같은 동작을 합니다. `status`는 준비 상태를 출력합니다.

전원을 켰을 때 처음 선택된 대상은 PC A입니다. 기본 페어링은 Just Works 방식이며,
암호화·본딩과 두 입력 리포트의 구독을 확인한 연결에만 입력을 보냅니다.
최대 2개 연결과 8개 상대 identity를 저장하며, PC 한 슬롯당 동시 연결은 1개입니다.
새 상대 등록은 등록 창이 열려 있을 때만 허용합니다.

듀얼 부팅 시에는 위 B 자동 키 선택 절차로 두 OS를 한 번씩 등록합니다.
OS가 자동 재연결하지 않으면 Bluetooth 설정에서 연결을 선택하세요.

## 전환

- 기본: **마우스 HID 4번 버튼(보통 뒤로 가기)**의 누름 순간마다 A ↔ B 전환
- 보조 단축키: **Ctrl + Alt + F12**
- COM 명령: `a` 또는 `b`

현재 Lift 리시버의 Report-mode 버튼 배치는 아직 실제 하드웨어로 검증하지
않았습니다. 버튼 로그에서 뒤로 가기를 눌렀을 때 `buttons=0x08`인지 확인하세요.
앞으로 가기 버튼(보통 `0x10`)을 전환용으로 쓰려면 `idf.py -C test menuconfig` →
`USB BLE input switch` → `Mouse HID button used to switch PCs`를 5로 변경합니다.

전환 버튼 자체는 PC로 전달하지 않습니다. 대상 PC가 연결·암호화·구독을
마치지 않았다면 전환하지 않고 현재 PC를 유지합니다. 이전 PC에 모든 키·버튼
해제를 보낸 후 새 PC로 전달하며, 전환 순간 누르고 있던 키·버튼은 한 번 놓은 뒤
다시 눌러야 새 PC로 전달됩니다. 마우스 움직임은 이후 리포트부터 새 PC로 갑니다.
이전 PC의 해제 리포트를 전송하지 못하면 최대 3초 동안 재시도합니다. 이후에는
그 연결로 새 입력을 보내지 않도록 제외하고 연결 종료를 요청하며, 정상 PC로의
입력 차단은 해제합니다. 이미 절전·구독 해제 상태인 이전 PC는 전환 시 즉시 제외합니다.
종료 요청이 실패하면 1초 간격으로 재시도하고, 요청이 접수된 경우에는 완료 이벤트를
기다립니다. 이 대기가 다른 PC를 막지는 않습니다. 종료 완료 전까지 이전 PC가
실제로 키 해제를 수신했다는 보장은 없으며, 종료 중인 PC로 다시 전환할 수는 없습니다.
재연결 시에는 중립 상태부터 시작하며 과거 입력을 재생하지 않습니다.

비선택 PC의 절전·복귀·구독 변경·연결 해제는 선택 PC의 누른 키·버튼 상태를
변경하지 않습니다. 절전된 PC로는 전환하지 않으며, 선택 PC가 절전된 경우에는
정상 PC로 전환 버튼/단축키를 눌러 전환합니다. 자동으로 입력 대상을 바꾸지는 않습니다.

## RGB LED 상태와 밝기

[YD-ESP32-S3 제조사 문서](https://github.com/vcc-gnd/YD-ESP32-S3/blob/main/README.md)에
따라 GPIO48의 WS2812 RGB LED를 사용합니다. 두 PC에 BLE 연결이 유지될 수 있으므로
A/B 색상은 **입력을 보내도록 선택한 PC**를 표시합니다.

| 상태 | LED 표시 |
| --- | --- |
| 앱 초기화 진행 중 (LED 초기화 이후) | **노랑, 계속 켜짐** |
| 인식된 USB 키보드·마우스가 모두 없음 (허브만 있는 경우 포함) | **빨강, 낮은 밝기로 계속 켜짐** |
| A 선택 + HID 전송 준비 완료 | **초록**, 약 1초 주기로 점멸 |
| B 선택 + HID 전송 준비 완료 | **파랑**, 약 1초 주기로 점멸 |
| USB 입력 장치는 있지만 선택한 PC가 준비되지 않음 | 해당 A/B 색, 약 2초마다 0.1초 짧게 점멸 |
| A/B 등록 모드 | 등록 대상의 같은 색, 약 0.25초 주기로 빠르게 점멸 |

부팅 중에는 노란색이 우선하며, 기본 초기화 완료 후 아래 연결 상태를 표시합니다.
등록 모드 표시가 빨간 ‘USB 장치 없음’ 표시보다 우선합니다. 등록이 완료되거나
취소·시간 만료되면 현재 상태 표시로 돌아갑니다. USB 장치 연결 상태를 별도로
추적하므로 키를 누르지 않는다고 빨간색으로 바뀌지 않습니다. 무선 리시버가
USB로 인식되어 있으면 입력 장치가 있는 것으로 봅니다.

기본 RGB 채널 값은 **2/255**로 낮췄습니다. 체감 밝기는 색상마다 다를 수 있습니다.
`idf.py -C test menuconfig` → `USB BLE input switch`에서 설정할 수 있습니다.

- `RGB channel brightness`: 0~255, 기본 2 (더 어둡게 하려면 1, 0은 끄기)
- `WS2812 GPIO`: 기본 48, 다른 보드 변형이면 실제 RGB 핀에 맞춰 변경
- `Use onboard WS2812 RGB status LED`: 상태 LED 기능 켜기/끄기

이 설정은 RGB LED에 적용됩니다. LED 갱신은 별도 태스크에서 수행하여
LED 전송 대기가 BLE HID 입력 처리를 막지 않도록 했습니다.

## COM 명령

| 명령 | 동작 |
| --- | --- |
| `pair a`, `pair b` | 해당 PC 슬롯으로 120초 등록 허용 |
| `pair off` | 등록 창 닫기 |
| `a`, `b` | 준비된 해당 PC로 전환 |
| `status` | 선택 대상, 준비 상태, 저장된 슬롯 확인 |
| `forget a`, `forget b` | 해당 PC 슬롯의 모든 등록 identity·본딩 정보 제거 |
| `help` | 명령 도움말 |

`forget` 사용 후에는 해당 PC의 OS에서도 ESP USB Switch 등록을 제거하세요.

## 구현 범위

- USB 키보드·마우스 모두 Report 모드를 사용하며 디스크립터로 필드 위치를 해석합니다.
- 키보드 배열 형식과 NKRO 비트맵을 읽어 BLE 6-key keyboard 리포트로 변환합니다.
  6개 초과 일반 키 동시 입력은 HID ErrorRollOver로 알립니다.
- 마우스 버튼 1~8, 상대 X/Y, 세로 휠, 가로 휠을 지원합니다.
  출력 범위는 X/Y signed 16-bit, 휠 signed 8-bit(-127~127)입니다.
- 리시버의 별도 일반 HID 인터페이스는 USB Host 채널을 아끼기 위해 열지 않습니다.
  따라서 그 인터페이스에만 있는 제조사 기능·미디어 키 등은 전달하지 않습니다.
- Caps/Num/Scroll Lock LED 출력은 BLE 연결별로 수신하지만 USB 키보드 LED로
  되돌려 보내는 기능은 없습니다.
- 파서는 Report ID, 비트 오프셋, signed 필드, Global Push/Pop을 처리합니다.
  입력은 최대 64바이트, report ID별 레이아웃은 최대 16개, 관련 필드는 최대 128개입니다.
  지원하지 않거나 너무 큰 디스크립터는 추측해서 전송하지 않고 로그를 남깁니다.
- 입력 큐가 넘치면 키·버튼을 해제하며, 과부하 중 일부 입력은 유실될 수 있습니다.
- USB 입력별 로그는 기본적으로 꺼져 있습니다. 높은 폴링률에서는 UART 출력이
  병목이 될 수 있으므로 `Print decoded USB input reports`는 진단할 때만 켜세요.

## 마우스 지연 진단

USB 입력은 BLE 호스트에 이벤트를 보내 즉시 처리하며, 10ms 타이머는 유지 관리와
전송 재시도에 사용합니다. 암호화된 연결에는 7.5~15ms 연결 간격과 latency 0을
요청합니다. 실제 적용값은 PC가 결정하며 연결 로그와 `status`에서 확인할 수 있습니다.

BLE 알림 전송이 일시적으로 실패하면 마우스 이동량을 보관해 재시도합니다.
같은 버튼 상태의 이동량은 합산하고, 버튼 상태가 바뀌는 순서는 유지합니다.
키보드는 최대 32개의 상태 변화를 순서대로 보관하므로, 전송 실패 중에도
`누름 → 뗌 → 다시 누름`의 중간 해제가 덮어써지지 않습니다.
보관 큐가 가득 차거나 전송 적체가 250ms 이상 지속되면 이전 입력을 폐기하고
키·버튼을 해제합니다. USB→BLE 입력 큐에서도 250ms 이상 된 입력은 재생하지 않습니다.
과부하 복구 시 USB 입력의 최신 상태를 반영하며, 계속 누르고 있던 키는
한 번 뗀 뒤 다시 눌러야 전달됩니다. PC 전환 시에도 이전 대기 입력은 지웁니다.
해제 알림조차 3초 동안 보내지 못하면 해당 BLE 연결을 종료해 재연결하게 합니다.
정상적으로 길게 누르는 키에는 유지 시간 제한을 적용하지 않습니다.

`status`의 `pending_mouse`, `pending_keys`는 대기량,
`notify_failures`, `mouse_overflows`, `key_overflows`는 연결별 누적 실패 횟수,
`stale_drops`는 BLE 전송 적체를 시간 제한으로 폐기한 횟수입니다.
USB→BLE 입력 큐의 시간 초과·포화는 별도 로그로 확인합니다.

## USB 허브 후연결·수신 오류 복구

HID 드라이버 준비가 끝난 뒤 USB 루트 포트를 켭니다. 허브 하위 포트의 전원 안정화
대기 시간은 500ms, 리셋 복구 시간은 100ms로 설정합니다. HID 인터페이스를 발견한 뒤
250ms를 기다리고 초기화하며, 프로토콜 설정·디스크립터 요청·수신 시작이 실패하면
250ms 간격으로 재시도하고 반복 실패 시 2초 간격으로 늦춥니다.

USB 전송 오류는 키·버튼을 해제한 뒤 `stop → start`로 수신을 재개합니다.
키보드에는 SET_IDLE로 100ms 간격의 현재 상태 보고를 요청해 일시적으로 놓친
해제를 보정합니다. 이를 무시하거나 지원하지 않는 리시버도 있으므로,
일정 시간 입력이 없다는 이유만으로 정상적인 키 누름을 해제하지는 않습니다.
분리 콜백에서는 소스 재사용과 핸들 정리를 담당 작업으로 넘겨 초기화와의 충돌을 줄입니다.

동작 중인 키보드·마우스 인터페이스가 10초 동안 하나도 없으면 루트 포트를
500ms 동안 끈 뒤 다시 켜서 HID 연결 이벤트 이전의 인식 실패도 재시도합니다.
입력 장치가 없는 동안에는 이 복구를 반복합니다. 하나라도 동작 중이면 전체 허브를
재시작하지 않습니다. 이는 USB 포트 재초기화이며 외부 전원 허브의 실제 전원 차단은 아닙니다.

기존 `test/sdkconfig`가 있으면 `sdkconfig.defaults`의 새 값이 자동으로 덮어써지지
않을 수 있습니다. `idf.py -C test menuconfig`의 `Component config → USB-OTG →
Hub Driver Configuration`에서 다음 값을 확인하세요.

- Root Port: Reset recovery delay = 100ms
- Downstream Port: Reset recovery delay = 100ms
- Downstream Port: Custom bPwrOn2PwrGood value = 활성화, delay = 500ms

진단 로그는 `USB retry`, `transfer error`, `receiving`,
`No usable USB input ... restarting root port`로 구분됩니다.

COM의 `usb status`는 BLE 큐를 거치지 않고 USB 관리 태스크에 진단을 요청합니다.
인터페이스별 `callbacks`(수신 콜백), `decoded`(해석 후 전달), `read_errors`,
`decode_errors`, `transfer_errors`, `last_callback_ms`(마지막 콜백 이후 시간)를
출력합니다. 카운터는 해당 인터페이스가 새로 연결되면 초기화됩니다.
`Queued usb status`만 나오고 진단이 나오지 않으면 USB 관리 태스크의 진행 여부도
확인해야 합니다. 이 명령은 기존 BLE `status`와 함께 사용합니다.

입력이 실제로 멈춘 경우 먼저 `usb status`를 저장한 뒤 `usb reset`으로 USB 루트
포트를 500ms 동안 비활성화했다 다시 활성화할 수 있습니다. 성공적으로 재설정을
시작하면 기존 입력을 차단하고 키·버튼 해제를 요청하며, 분리 콜백을 기다려 이전
핸들을 정리합니다. BLE 페어링 정보는 유지됩니다. 별도 전원 허브의 실제 전원을
껐다 켜는 동작은 아니므로 물리적 재연결과 같은 복구 효과를 보장하지는 않습니다.
정상적인 무입력 상태를 장애로 오인하지 않도록 무입력 시간만으로 리셋하지 않습니다.

USB 상태 감시는 수신 중인 HID 장치를 주소별로 감시합니다. 같은 리시버의 키보드와
마우스는 한 장치로 묶으며, 최근 1초 구간에 리포트 8개 이상을 받은 경우 이후
3초 동안, 또는 키·버튼이 눌린 상태에서는 0.5초간 콜백이 없으면 검사합니다.
그 외에는 5초 무입력 후 표준 장치 `GET_STATUS` 요청을
비동기로 보냅니다. 정상 완료 또는 STALL(요청 거부 응답)이면 응답 가능한 장치로
판단해 입력을 해제하거나 리셋하지 않습니다. 계속 조용하면 1초 간격으로 확인합니다.
완료된 전송 오류가 3회 이어지거나, 제출된 요청이 0.5초 뒤에도 완료되지 않고 1초
간격의 추가 확인 2회에서도 완료되지 않으면 `Automatic USB root restart`로
복구합니다. 새 입력 또는 정상/거부 응답은 실패 횟수를 초기화합니다.
자동 복구 요청/USB 재설정 후 60초간은 새 상태 요청과 자동 복구를 쉬며,
`usb reset` 수동 명령은 계속 사용할 수 있습니다.

`usb status`에는 `usb_health`의 주소별 `probes`, `replies`, `stalls`, `failures`,
`pending`, `gone`도 출력됩니다. 제출 자체의 로컬 오류는 로그만 남기며 자동 리셋의
근거로 삼지 않습니다. 제어 응답은 정상인데 인터럽트 입력만 멈추는 경우는 정상
무입력과 아직 구분할 수 없으므로 자동 수신 재시작을 하지 않습니다. 이때는 진단을
저장하고 수동 `usb reset`으로 복구해야 합니다. 상태 감시는 BLE와 독립적이며,
보드 전체 또는 USB 관리 태스크가 멈추는 경우까지 복구하는 watchdog은 아닙니다.

## 문제 및 수정 기록

### 2026-09-22 — 입력 적체와 USB 허브 후연결

- **보고된 문제:** 같은 키가 계속 눌리는 듯한 입력, 보드 전원을 먼저 켠 뒤
  허브를 연결하면 간헐적으로 키보드가 인식되지 않음.
- **확인한 코드 문제:** BLE 전송 실패 중 키보드의 중간 해제 상태가 최신 상태로
  덮어써질 수 있었음. USB 전송 오류 후 수신 재시작과 초기화 실패 재시도가 없었음.
- **수정:** 키 상태 변화의 순서를 보존하는 32개 대기열 추가, 250ms 이상 적체 폐기와
  중립 상태 전송, 입력 큐 손실 시 최신 USB 상태 복원 및 계속 누른 단축키 재실행 방지.
  USB 초기화 재시도, 오류 후 stop/start, 허브 안정화 대기와 입력 장치가 없는 경우
  루트 포트 재초기화를 추가함.
- **검증:** 빌드 및 파서·라우터·키보드/마우스 대기열·USB 복구 테스트 통과.
  적용 후 사용자의 초기 정상 동작 보고가 있었으나 장시간 무결함을 확인한 것은 아님.

### 2026-09-22 — Espressif IDE 인식·Python·No binaries

- **보고된 문제:** 프로젝트 인식 실패, `/usr/bin/python`에서 `idf_component_manager`
  모듈을 찾지 못함, 실행 시 `No binaries` 발생.
- **확인한 설정 문제:** `test`가 일반 CMake 프로젝트로 등록되어 `Local` 타깃과
  PC용 실행 구성을 사용했음. ESP-IDF 전용 Python에는 필요한 모듈이 이미 있었음.
- **수정:** 로컬 `test/.project`를 ESP-IDF nature로 수정하고,
  `test/test-esp32s3.launch`에 `ESP-IDF Application` 실행 구성을 추가함.
  실제 프로젝트 루트는 `test/`이며 `test/main/`은 독립 프로젝트가 아님.
- **적용:** 프로젝트를 새로고침하고 `Run / test-esp32s3 / esp32s3` 및 해당 시리얼
  포트를 선택. `.project`는 Git에서 제외된 로컬 설정이므로 새 환경에서는
  `Import → Espressif → Existing IDF Project`로 `test/`를 가져와야 함.
  Build는 컴파일, ESP-IDF 구성의 Run/Launch는 보드 업로드에 사용함.

### 2026-09-22 — 비선택 PC 절전 시 선택 PC 입력 정지

- **보고된 상황:** 양쪽 PC가 연결된 상태에서 **입력 대상이 아닌 PC**가 절전에
  들어가자 선택 PC로도 입력이 전달되지 않았고 전환 키도 효과가 없었음.
  허브를 재연결하고 절전 PC를 깨운 뒤 복구됨. 보드 COM/UART 전원은
  절전 PC가 아니라 **계속 켜져 있던 PC**에서 공급되었음.
- **확인·재현 1:** 어느 PC의 절전·복귀·구독 변경·암호화·연결 해제 이벤트든
  공통 라우터의 누른 키·버튼을 차단했음. 비선택 PC의 Suspend 이벤트로
  선택 PC의 유지 중인 키가 해제되는 것을 수정 전 호스트 테스트에서 재현함.
- **확인·재현 2:** PC 전환 후 이전 PC의 해제 전송이 실패하면 새 PC를 차단하고,
  3초 후 연결 종료를 요청하더라도 완료 이벤트까지 차단을 유지했음.
  종료 요청이 실패하는 상황에서 3초 후에도 차단되는 것을 테스트로 재현함.
  이는 전환/연결 정리의 추가 결함이며, 비선택 PC 절전 자체의 확정 원인은 아님.
- **수정:** 연결 상태 변화로 인한 누른 입력 차단은 해당 PC가 선택된 경우에만 적용.
  중복 Suspend/구독 이벤트는 무시. 종료 중인 연결은 입력 대상에서 제외하여
  다른 PC를 막지 않도록 하고, 종료 요청 반환값과 비동기 실패 이벤트를 처리함.
  실패 시 1초 간격 재시도, 이미 종료 중이면 중복 요청 억제, 이미 끊겼으면 상태 정리.
  공유 BLE 알림 버퍼는 선택 PC가 먼저 사용하도록 처리 순서를 변경함.
- **검증:** 수정 전 위 두 테스트의 실패를 확인한 뒤 수정 후 통과.
  비선택 PC 절전/복귀/분리, 선택 PC 절전 후 수동 전환, 늦은 분리 이벤트,
  재연결 후 중립 상태, 해제 시간 초과, 종료 요청 실패·진행 중·연결 없음,
  제한된 전송 버퍼에서 선택 PC 우선 처리도 테스트함. 펌웨어 빌드 및 기존 회귀 테스트 통과.
- **남은 확인:** 공통 키 차단은 키·버튼 유지 문제를 설명하지만, 보고된 마우스 이동까지
  포함한 전체 정지의 원인을 모두 확정한 것은 아님. 실기기 재현 당시 로그가 없어
  USB 전원/수신 상태와 BLE 무선·컨트롤러 정체는 추가 확인이 필요함.

### 2026-09-22 — 허브 수신 정지·마지막 키 반복 재발

- **추가 보고:** PC 절전과 무관하게 입력과 전환 키가 모두 먹통이 되는 현상이 재발함.
  타이핑 중 발생하면 마지막 키가 반복되며, 두 경우 모두 허브를 뺐다 끼우면 복구됨.
  따라서 앞서 보고된 절전 시점만으로 BLE 절전이 전체 정지 원인이라고 볼 수 없음.
- **코드에서 확인한 결함:** USB HID 드라이버 1.2.1의 `in_xfer_done()`이 리포트를
  전달한 뒤 `usb_host_transfer_submit()`으로 다음 수신을 예약하면서 반환값을 무시함.
  예약 실패 시 오류 이벤트도 발생하지 않아 앱이 수신 중 상태로 남고,
  기존 오류 기반 stop/start와 입력 장치 없음 기반 루트 포트 복구가 작동하지 않음.
  키 해제 리포트를 놓치면 PC의 자동 반복으로 마지막 키가 계속 입력될 수 있음.
- **수정:** 재예약 실패를 `IN transfer resubmit failed: ...`로 기록하고
  `TRANSFER_ERROR`를 전달하도록 수정. 기존 앱 처리가 누른 입력을 해제하고,
  관리 태스크에서 endpoint stop/start를 재시도함. 관리 구성 요소를 직접 고치지 않고
  `test/components/usb_host_hid`에 원본 라이선스를 포함한 1.2.1 기반 소스를 두고
  manifest의 `override_path`로 지정해 클린 빌드에서도 수정이 유지되게 함.
- **검증:** 실제 드라이버 콜백을 컴파일해 재예약 성공/실패, 전송 오류, 취소,
  장치 분리의 이벤트와 재예약 횟수를 확인함. 기존 USB 복구·BLE 절전·입력 회귀
  테스트 및 ESP-IDF 6.1 / ESP32-S3 빌드 통과. LED 동작은 유지함.
- **한계:** 이 실패 경로의 결함은 확인했지만, 실제 멈춤 당시의 로그가 없어 이번
  증상의 확정 원인은 아님. 예약이 성공한 채 허브/호스트가 응답하지 않는 정체는
  이번 수정으로 감지하지 못함. 정상적인 무입력과 구분할 근거 없이 시간만으로
  USB를 재설정하거나 유지 중인 키를 해제하는 동작은 추가하지 않음.

재발 시 재부팅·허브 재연결 전에 가능하면 COM에서 `status`를 입력해 로그를 남깁니다.
이번 수정의 `IN transfer resubmit failed` 및 기존 `Transfer failed`/USB 복구 로그도
함께 확인합니다. 전환 키도 같은 USB 수신 경로를 쓰므로 수신 중단 시 작동할 수 없습니다.
`USB sources`는 인식된 입력 인터페이스, `reports`는 USB 입력 큐에 제출된 누적 리포트 수입니다.

  자동 판별하지 못하며 수동 usb reset이 필요할 수 있음.
- **검증:** 실제 감시 코드로 최근 입력 급감, 움직이다 멈춘 정상 상태, 리포트가
  반복되지 않는 길게 누르기, 해제 후 일반 검사 복귀와 기존 실패/분리/복구
  테스트 통과. ESP32-S3 빌드 검증. 보드 업로드와 실기기 재현 확인은 아직 하지 않음.

### 2026-09-23 — 부팅 중 노란색 LED 표시

- **문제:** 초기화 중과 초기화 완료 후 USB 입력 장치가 없는 경우 모두 빨간색으로
  보여 부팅 진행 상태를 구분하기 어려웠음.
- **수정:** LED 초기화 직후 노란색으로 점등하고 BLE/USB 초기화 및 콘솔 태스크
  생성이 끝난 시점에 기존 연결 상태 표시로 전환함. BLE 태스크가 먼저 상태를
  갱신해도 초기화 완료 전에는 노란색을 유지함. 완료 시
  `Board initialization complete` 로그를 남김. A/B 색을 반대로 쓰던 부팅 로그도
  실제 패턴과 일치하도록 정정함. 이후 빨강/초록/파랑의 기존 패턴은 유지함.
- **의미/한계:** 노랑은 앱 초기화 진행 중, 빨강은 초기화 이후 USB 입력 소스 없음.
  완료 표시는 PC 연결이나 모든 USB 장치 인식 완료를 보장하지 않음. ROM/부트로더
  단계와 LED 초기화 실패에서는 노란색을 보장하지 않으며, 실행 중 멈춤을 판정하는
  표시도 아님. ESP32-S3 빌드 확인, 보드 업로드 및 실제 색 확인은 아직 하지 않음.

### 2026-10-07 — 듀얼 부팅 OS 변경 후 PC B 인증 실패

- **로그:** PC B가 연결 직후 encryption/bond 실패로 분리되는 과정을 반복함.
  `reason=573`은 NimBLE HCI 기준값 0x200 + 0x3D(MIC 무결성 검증 실패)임.
  status는 A-ready=1, B-ready=0, A의 암호화/구독 정상으로 나타남.
- **해석:** B의 인증이 완료되지 않아 전환 대상 준비 조건을 만족하지 못함.
  동일 OS에서는 연결되고 다른 OS로 바꿀 때 실패한다는 보고와 함께 보면,
  동일 Bluetooth identity를 공유하는 OS 사이 본딩 키 불일치가 유력함.
  MIC 오류만으로 키 불일치를 확정할 수는 없으며 OS 종류·identity 비교는 미확인.
  광고 rc=6도 동반되지만 인증 실패와 구분해서 봐야 함.
- **대응:** 현재 OS의 기존 장치 등록 제거 및 B 등록 모드에서 재페어링은 단기
  복구 방법임. 같은 identity를 쓰는 다른 OS의 키가 다시 불일치할 수 있어,
  반복 재페어링만으로 듀얼 부팅 문제가 해결됐다고 판단하지 않음.
  OS별 identity 분리 또는 OS 간 본딩 정보 일치 여부를 확인해야 함.
  이번에는 진단을 기록했으며 페어링 정보 삭제나 펌웨어 수정은 수행하지 않음.

### 2026-10-07 — OS 프로필 분리 및 키보드 잠금 LED 출력

- **문제:** 노트북의 Windows/Ubuntu가 같은 Bluetooth identity에 서로 다른 키를
  사용해 암호화 인증이 반복 실패함. PC의 키보드 LED 출력은 저장만 하고 USB에
  전달하지 않아 Caps Lock/Num Lock 표시도 갱신되지 않았음.
- **OS 수정:** 두 개의 영구 static-random 주소와 장치 이름, A/B 목록을 분리함.
  SDK의 `nimble_bond` NVS 접근을 링크 wrapper로 프로필별 namespace에 연결하여
  본딩 키뿐 아니라 IRK/CCCD 저장도 분리함. SDK 원본은 변경하지 않음.
  실제 ELF에서 NimBLE NVS read/write가 wrapper를 호출하는 것을 확인함.
  활성 프로필은 재부팅 전에 저장하되 런타임 주소/namespace는 부팅 전까지 바꾸지 않음.
  전환 중 신규 입력·등록을 차단하고 해제를 먼저 시도하며, 종료가 지연되면 최대
  6초 뒤 저장/재부팅함. 저장 오류 시 현재 프로필을 유지하고 재부팅하지 않음.
- **LED 수정:** HID Output 디스크립터의 LED usage와 비트 위치/report ID를 해석함.
  선택된 PC의 LED 상태를 비동기 SET_REPORT(Output)로 키보드에 전달하고 A/B 전환,
  USB 재연결 시 재반영함. 전송 중 데이터는 변경하지 않고 최신 상태를 대기시킴.
  다른 기능이 섞인 Output/지원하지 않는 형식은 임의로 쓰지 않으며, STALL 또는
  반복 출력 오류 시 해당 출력은 재연결 전까지 중단함. 제조사 전용 표시나 USB
  Output 리포트로 LED를 제공하지 않는 리시버는 지원이 제한될 수 있음.
- **검증:** 프로필 주소 유지·분리, namespace 선택, 재부팅 경계, 저장 실패,
  입력 해제 후 프로필 전환, 강제 종료 기한, A/B별 LED 상태 선택, LED report ID/
  padding/비트 배치, 전송 중 상태 변경·거부 응답을 호스트 테스트로 검증함.
  기존 입력/USB/BLE 회귀 테스트 및 ESP-IDF 6.1 ESP32-S3 빌드 통과.
  실제 Windows/Ubuntu 교대 부팅 및 키보드 표시 검증은 아직 필요하며 업로드하지 않음.

### 2026-10-07 — OS 자동 구분 가능성 진단 명령

- **목적:** 동일 어댑터의 두 OS를 본딩 목록에서 자동 선택할 수 있는지 확인하기
  위해 COM `os inspect`를 추가함. 현재 프로필의 B 저장 identity, IRK 존재 여부와
  SHA-256 앞 16바이트 지문, Secure Connections 여부, 연결 중 identity/실제 연결
  주소와 RPA 여부를 출력함. LTK/IRK 원문은 출력하지 않으며 저장 정보는 변경하지 않음.
- **실행:** Ubuntu 프로필에서 노트북 Ubuntu를 B에 연결한 뒤 `status`, `os inspect`를
  실행하고, Windows 프로필에서 노트북 Windows를 B에 연결한 뒤 같은 명령을 실행함.
  아직 등록하지 않은 프로필은 `pair b`로 한 번 등록해야 함. 양쪽에서 재연결 후
  한 번 더 수집하면 식별 정보의 안정성도 비교할 수 있음.
- **판단:** 다른 peer identity는 직접 구분 후보, 다른 IRK와 실제 RPA 사용은
  IRK 기반 주소 해석 후보임. 같은 public/static 주소로 연결한다면 IRK 지문만
  다르다고 연결 전 자동 선택이 가능해지는 것은 아님. RPA 판별은 현재 연결 주소의
  형식 확인이며 향후 OS의 모든 연결 방식을 보장하지 않음. 현재 펌웨어는 아직
  자동 OS 선택을 하지 않음.
- **검증:** ESP32-S3 빌드, B만 대상으로 저장소를 읽고 프로필/등록을 변경하지 않는
  호스트 회귀 테스트 통과. 실기기 비교 결과와 SHA 지문 출력 확인은 대기 중.

### 2026-10-07 — 새 B 페어링 시 PC 이름 조회

- **요청:** B 등록을 정리한 뒤 새 연결에서 OS 이름도 함께 확인.
- **수정:** B 연결 직후 Device Name(0x2A00)을 GATT로 조회함. 앱이 시작하는
  암호화 요청은 조회 완료/실패 또는 2초 경과까지 미루고, 이후 정상 인증을 진행함.
  PC가 먼저 암호화를 시작할 수도 있으므로 이름 로그에 encrypted_at_reply를 함께
  기록함. 조회 결과는 `os inspect`에도 표시되며 이름으로 인증하거나 프로필을
  자동 선택하지는 않음. 늦은 응답은 연결별 토큰으로 구분함.
  SDK의 GATT client 의존성에 맞춰 Central/GATT client 빌드 옵션을 활성화했지만
  보드가 PC를 스캔하거나 접속을 시작하는 동작은 추가하지 않음.
- **등록 정리 절차:** 해당 OS의 기존 보드 등록을 제거하고, 펌웨어 업로드 후
  대상 프로필을 선택해 COM에서 `forget b`, `pair b`를 순서대로 실행함.
  forget b는 현재 프로필의 B만 지우며 A와 다른 프로필의 B는 유지함.
  다른 프로필도 정리하려면 그 프로필로 전환한 뒤 같은 명령을 실행함.
  새 페어링의 연결 로그와 `status`, `os inspect`를 OS별로 수집함.
- **검증/상태:** 이름 응답, 늦은/중복 토큰, 2초 제한, 제출 실패 후 인증 진행을
  호스트 테스트로 확인함. 현재 작업 환경에 COM 장치가 노출되지 않아 실제 보드의
  등록 삭제와 업로드는 수행하지 못함. 실기기 이름 조회 가능 여부는 확인 대기 중.

## 검증 상태

사용자 보드에서 USB 허브 재연결과 키보드·마우스 수신, BLE 동작이 보고되었습니다.
키보드 대기열·USB 복구 수정 후 사용자가 초기 정상 동작을 보고했으나,
이후 비선택 PC 절전 시, 그리고 절전과 무관하게 전체 입력이 멈추는 증상이 추가 보고되었습니다.
이번 USB 재예약 오류 처리 및 BLE 절전/연결 정리 수정은 ESP-IDF 6.1 / ESP32-S3 빌드와
ASan/UBSan 호스트 회귀 테스트를 통과했습니다. 이번 수정본은 아직 보드에 업로드하지 않았으며,
비선택 PC 절전·종료·복귀와 실제 무선 혼잡 상황은 실기기 검증이 필요합니다.

저장소 최상위에서 파서·전환 로직 테스트:

```sh

  test/main/mouse_pending.c test/main/keyboard_pending.c test/tests/test_input.c \

ASAN_OPTIONS=detect_leaks=0 /tmp/test-esp-hid
```

테스트는 사용자 로그의 05AC:024F 및 046D:C548 키보드 디스크립터, 합성 마우스
디스크립터, 짧거나 잘못된 데이터, 잘못된 디스크립터 10,000개, 키 해제·동시 입력,
전환 버튼 유지·재누름, 비연결 대상 전환 거부, 등록 단축키의 반복·해제·충돌 처리,
source 분리, USB 장치 없음/연결 대기/선택 PC/등록 모드의 LED 색과 점멸 주기를 확인합니다.

### 2026-10-07 — B 노트북 이름으로 OS 본딩 키 자동 선택

- 문제: 같은 공개 주소의 Windows/Ubuntu가 서로 다른 키를 사용해 암호화에 실패했습니다.
  실측 이름은 Windows `DESKTOP-36CBTO9`(끝 NUL이 과거 로그에서 `?`로 표시), Ubuntu `jsy`이며
  모두 `encrypted_at_reply=0`에서 읽혔습니다.
- 수정: 보드 전체 프로필 자동 전환 대신 B의 OUR_SEC/PEER_SEC 키를 OS별 NVS 레코드에

### 2026-10-07 — B의 45ms 연결 간격과 rc=530 대체 요청

- 관측: A=15ms, B=45ms이며 B의 GAP/HCI 간격 단축 요청이 `rc=530`
  (`BLE_ERR_INV_HCI_CMD_PARMS`)으로 세 번 실패했습니다. 해당 USB 상태는 마우스의
  마지막 수신 5ms, 오류 0으로, 그 측정에서 USB 정지는 확인되지 않았습니다.
- 수정: 이미 7.5–15ms/latency=0인 연결에는 요청하지 않습니다. HCI 파라미터 오류가
  발생하면 2초 뒤 L2CAP Connection Parameter Update Request로 중앙 장치(PC)에
  7.5–15ms/latency=0/timeout=4s를 요청합니다. SDK는 LL 기능 미지원에는 자체 대체 경로가
  있지만 이번 HCI 파라미터 오류에는 자동 전환하지 않아 앱에서 처리합니다.
- 제한: 총 요청은 연결당 최대 세 번입니다. L2CAP 응답 실패 후에는 5초 대기합니다.
  오래된 콜백은 요청 토큰으로 무시합니다. 수락 응답은 실제 간격 변경과 같지 않으며,
  이후 `PC B BLE interval=...` 및 `status`로 확인해야 합니다. PC가 짧은 간격을
  허용하지 않으면 45ms가 유지될 수 있고, 양쪽 버벅임의 모든 원인을 해결했다는 뜻은 아닙니다.
- 검증: 15ms 연결 요청 생략, 530 대체 경로, 재시도 간격/횟수 제한, 오래된 콜백 무시,
  기존 GAP 성공 경로와 BLE 입력/해제 회귀 테스트 통과. 하드웨어 확인은 별도입니다.
- 적용: 빌드 후 업로드하고 B를 연결합니다. 페어링 정보 삭제는 필요 없습니다.
  `requested 7.5-15 ms via L2CAP: rc=0`은 요청 제출 성공이며 최종 간격을 확인하세요.

### 2026-10-07 — 7.5ms 고정 간격 요청 시험

- 관측: 재접속 후 A/B가 모두 15ms로 연결됐고 사용자가 움직임이 부드러워졌음을 확인했습니다.
  더 짧은 간격을 시험하기 위해 요청 범위를 7.5–15ms에서 7.5ms로 변경합니다.
- 수정: GAP/HCI 및 L2CAP 모두 최소/최대 간격을 6(1.25ms 단위), latency=0,
  supervision timeout=4초로 요청합니다. 이미 7.5ms/latency=0일 때만 생략하고
  15ms 연결에서도 요청합니다. 기존 대체 경로와 연결당 최대 세 번 제한은 유지합니다.
- 검증: 두 요청 경로의 최소/최대 값, 15ms에서도 요청하는 동작, 7.5ms 생략,
  대체 요청 및 재시도 제한을 포함한 BLE 회귀 테스트 통과.
- 적용/판정: 업로드 후 재페어링 없이 연결하고 `status`의 실제 `BLE interval=7.50 ms`를
  확인합니다. 요청의 rc=0만으로 7.5ms가 적용됐다고 판단하지 않습니다. PC가 거절하거나
  다른 간격을 유지할 수 있으며, 실제 부드러움과 두 연결의 안정성은 하드웨어에서 확인합니다.

### 2026-10-12 — B의 이름 조회/암호화 순서 경쟁으로 재접속 반복

### 2026-10-12 — 저장된 B 키의 제한적 순차 인증

- 관측: 이전 LTK 대기 방식에서 이름 응답이 계속 시간 초과됐습니다. 인증 전에 이름을
  알아야 한다는 조건 때문에 두 OS의 키가 저장돼 있어도 재접속하지 못했습니다.
- 수정: 기존 등록 재접속은 이름 조회 없이 후보 키를 먼저 선택하고 즉시 인증합니다.
  마지막 성공 후보를 NVS `last_ok`에 저장하며, 없으면 Ubuntu 키부터 존재 여부를 확인합니다.
  인증 후 이름을 읽되 이름 실패/변경으로 키를 바꾸거나 정상 연결을 끊지 않습니다.
- 후보 전환: 실제 OUR_SEC 키를 조회한 연결에서 HCI Authentication Failure(0x205),
  PIN/Key Missing(0x206), MIC Failure(0x23d)를 받으면 해당 후보만 실패로 표시합니다.
  ENC_CHANGE와 DISCONNECT의 중복 오류는 한 번만 반영합니다. 다음 재접속 때 다른 후보를
  사용하며, 두 후보가 모두 실패하면 더 이상 키로 인증하지 않습니다. 인증 성공 시 실패 기록을
  초기화합니다. `os retry` 또는 보드 재부팅으로 시도를 재개할 수 있으며 키는 삭제하지 않습니다.
- 보존: 등록 창 밖에서 키 교체/삭제 금지를 유지합니다. A 저장 경로 및 7.5ms 요청도 유지합니다.
  `pair b` 신규 등록은 이름으로 저장 영역을 고르는 기존 경로를 사용하므로 이름 응답이 필요합니다.
- 검증: Windows→Ubuntu 및 역방향 후보 전환, 성공 후보의 재부팅 후 우선순위,
  일반 종료/타임아웃 무시, 중복 오류, 두 후보 소진, 수동 재시도 및 키 보존 테스트 통과.
  BLE 이벤트 테스트에서 인증 전 이름 불필요, 인증 후 이름 실패에도 연결 유지 확인.
  ESP-IDF v6.1 빌드 통과. 실제 PC의 인증 실패 후 재접속 정책은 하드웨어 확인이 필요합니다.
- 확인 로그: `trying saved Ubuntu/Windows key` → 실패 시 다음 재접속의 다른 후보 →
  `bonded and encrypted`를 확인합니다. PC가 일반 종료 코드만 보내는 경우에는 후보를
  자동 전환하지 않으므로 실패 직전부터 로그가 필요합니다.
