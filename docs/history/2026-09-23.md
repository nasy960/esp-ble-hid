## 오류 없는 수신 정지와 소프트웨어 재설정 복구 확인

- **정지 시 진단:** `reports=41032`이며 세 인터페이스가 stage=5/accepting=1로
  남아 있었음. 약 74초 간격의 두 진단에서 callbacks/decoded가 그대로였고,
  read/decode/transfer 오류는 모두 0. Logitech 두 인터페이스는 reset 직전
  마지막 콜백 이후 약 138초가 경과함. BLE status는 정상 응답하고 양쪽 PC가 ready,
  대기열과 notify_failures는 0이었음. 기존 오류 이벤트 기반 복구로는 감지하지
  못하는 수신 콜백 중단을 관찰함.
- **실기기 복구:** 물리적 분리 없이 `usb reset`으로 루트 포트를 재시작하고 약
  3.8초 뒤 Logitech 키보드/마우스가 receiving에 도달함. 사용자가 입력 복구를 확인함.
  분리 정리 중 EP INVALID_STATE 로그가 있었지만 이번에는 재인식을 막지 않았음.
- **복구 후 진단:** addr=6 iface=0은 callbacks=decoded=745, 마지막 콜백 28ms 전,
  iface=1은 callbacks=decoded=38, 마지막 콜백 약 51초 전이며 오류는 모두 0임.
  마우스의 무입력 시간만으로 재정지를 판단할 수는 없음. source 번호는 재연결 시
  바뀌었으므로 주소/인터페이스와 VID/PID로 대응시킴.
- **별도 확인:** Apple addr=5 iface=0은 callbacks=2, decoded=0, read_errors=2였음.
  현재 read_errors는 API 읽기 실패뿐 아니라 길이 0 리포트도 포함하므로 실제 읽기
  오류로 단정하지 않음. Apple 키보드를 직접 누른 전후의 카운터와 동작 확인이 필요함.
- **판단 범위:** 소프트웨어 USB 재초기화로 복구되는 것은 확인했으나 허브·호스트
  컨트롤러·드라이버 중 최초 원인 및 전원과의 연관성은 아직 미확정임. 이번 로그
  해석에서는 펌웨어를 추가 변경하지 않음.

## 비동기 상태 확인과 조건부 자동 USB 복구

- **문제:** HID 인터페이스가 수신 중으로 남은 채 콜백만 멈추면 기존 오류 기반
  복구로는 발견할 수 없었음. 사용자가 제어 요청 기반 감시 구현을 승인함.
- **수정:** 별도 USB 비동기 클라이언트가 장치 핸들과 전송 버퍼를 소유하고
  표준 GET_STATUS 응답을 확인하도록 `usb_health.c`를 추가함. HID 드라이버의
  동기 요청 버퍼를 공유하지 않고, 모든 감시 API는 USB 관리 태스크에서 실행함.
  현재 USB 전송 구조체의 timeout_ms는 미지원으로 명시되어 있어 자체 시계로
  미완료 요청을 관찰함. 완료 콜백 전에는 버퍼를 재제출/해제하지 않으며,
  분리 시에도 완료를 기다린 뒤 클라이언트 핸들을 닫음.
- **판단/복구:** 30초 무입력은 검사 시작 조건일 뿐 장애 판정이 아님. 정상 응답과
  STALL은 살아 있다는 근거로 처리하고, 반복 전송 실패/지속 무응답만 기존 루트
  재시작 처리에 연결함. 입력만 멈추고 제어 응답은 살아 있는 경우의 자동 복구는
  오탐 없는 판정 근거가 없어 보류함. LED 패턴과 페어링 정보는 변경하지 않음.
- **검증:** 실제 감시 코드를 가상 시계와 USB 대역으로 실행해 정상 무입력,
  거부 응답, 반복 오류, 완료 콜백 누락, 새 입력에 의한 실패 해제, 60초 간격 제한,
  로컬 제출 실패, 요청 중 분리와 늦은 완료, 핸들 닫기 재시도를 확인함.
  USB 복구 회귀 및 ESP-IDF 6.1 / ESP32-S3 빌드 통과. 실기기 장시간 검증과
  해당 정지 상황에서 제어 요청 응답 여부 확인은 아직 필요함. 보드 업로드는 하지 않음.

## 최근 입력량·눌림 상태에 따른 빠른 상태 검사

- **요청:** 사용 중 갑자기 멈출 때 고정 30초 대기가 길고, 키/버튼 해제를 놓치면
  PC에서 누름 상태가 지속되므로 최근 입력량에 따라 더 빨리 확인하도록 변경 요청.
- **수정:** 주소별 리포트 누적 수를 모아 1초 구간의 증가량을 계산함. 8개 이상의
  입력이 관찰되면 마지막 증가 이후 3초 동안 빠른 감시를 적용하고, 키/버튼이
  눌린 상태도 별도 빠른 조건으로 사용함. 빠른 조건의 검사 시작은 0.5초 무입력,
  일반 조건은 5초 무입력으로 단축. 제어 요청 응답 관찰 기한은 0.5초,
  재검사 간격은 1초로 줄임. USB status에 held/recent_reports/fast를 추가함.
- **해제 의미:** 무입력만으로 키를 해제하지 않음. 제어 무응답이 지속되면 빠른
  조건에서 대략 마지막 수신 3초 후 기존 키·버튼 해제 및 루트 재시작을 요청함.
  실행 지연, 다른 검사 요청, 재설정 후 60초 대기 제한에 따라 더 늦을 수 있음.
  PC의 반복 입력은 마지막 key-down 상태 유지로도 발생하며, 보드가 계속 새 키
  리포트를 보내고 있다는 뜻은 아님. 제어 응답만 살아 있는 입력 정지는 여전히
  자동 판별하지 못하며 수동 usb reset이 필요할 수 있음.
- **검증:** 실제 감시 코드로 최근 입력 급감, 움직이다 멈춘 정상 상태, 리포트가
  반복되지 않는 길게 누르기, 해제 후 일반 검사 복귀와 기존 실패/분리/복구
  테스트 통과. ESP32-S3 빌드 검증. 보드 업로드와 실기기 재현 확인은 아직 하지 않음.

## 부팅 중 노란색 LED 표시

- **문제:** 초기화 중과 초기화 완료 후 USB 입력 장치가 없는 경우 모두 빨간색으로
  보여 부팅 진행 상태를 구분하기 어려웠음.
- **수정:** LED 초기화 직후 노란색으로 점등하고 BLE/USB 초기화 및 콘솔 태스크
  생성이 끝난 시점에 기존 연결 상태 표시로 전환함. BLE 태스크가 먼저 상태를
  갱신해도 초기화 완료 전에는 노란색을 유지함. 완료 시
  `Board initialization complete` 로그를 남김. A/B 색을 반대로 쓰던 부팅 로그도
  실제 패턴과 일치하도록 정정함. 이후 빨강/초록/파랑의 기존 패턴은 유지함.
- **의미/한계:** 노랑은 앱 초기화 진행 중, 빨강은 초기화 이후 USB 입력 소스 없음.
  완료 표시는 PC 연결이나 모든 USB 장치 인식 완료를 보장하지 않음. ROM/부트로더
  단계와 LED 초기화 실패에서는 노란색을 보장하지 않으며, 실행 중 멈춤을 판정하는
  표시도 아님. ESP32-S3 빌드 확인, 보드 업로드 및 실제 색 확인은 아직 하지 않음.
