## 듀얼 부팅 OS 변경 후 PC B 인증 실패

- **로그:** PC B가 연결 직후 encryption/bond 실패로 분리되는 과정을 반복함.
  `reason=573`은 NimBLE HCI 기준값 0x200 + 0x3D(MIC 무결성 검증 실패)임.
  status는 A-ready=1, B-ready=0, A의 암호화/구독 정상으로 나타남.
- **해석:** B의 인증이 완료되지 않아 전환 대상 준비 조건을 만족하지 못함.
  동일 OS에서는 연결되고 다른 OS로 바꿀 때 실패한다는 보고와 함께 보면,
  동일 Bluetooth identity를 공유하는 OS 사이 본딩 키 불일치가 유력함.
  MIC 오류만으로 키 불일치를 확정할 수는 없으며 OS 종류·identity 비교는 미확인.
  광고 rc=6도 동반되지만 인증 실패와 구분해서 봐야 함.
- **대응:** 현재 OS의 기존 장치 등록 제거 및 B 등록 모드에서 재페어링은 단기
  복구 방법임. 같은 identity를 쓰는 다른 OS의 키가 다시 불일치할 수 있어,
  반복 재페어링만으로 듀얼 부팅 문제가 해결됐다고 판단하지 않음.
  OS별 identity 분리 또는 OS 간 본딩 정보 일치 여부를 확인해야 함.
  이번에는 진단을 기록했으며 페어링 정보 삭제나 펌웨어 수정은 수행하지 않음.

## OS 프로필 분리 및 키보드 잠금 LED 출력

- **문제:** 노트북의 Windows/Ubuntu가 같은 Bluetooth identity에 서로 다른 키를
  사용해 암호화 인증이 반복 실패함. PC의 키보드 LED 출력은 저장만 하고 USB에
  전달하지 않아 Caps Lock/Num Lock 표시도 갱신되지 않았음.
- **OS 수정:** 두 개의 영구 static-random 주소와 장치 이름, A/B 목록을 분리함.
  SDK의 `nimble_bond` NVS 접근을 링크 wrapper로 프로필별 namespace에 연결하여
  본딩 키뿐 아니라 IRK/CCCD 저장도 분리함. SDK 원본은 변경하지 않음.
  실제 ELF에서 NimBLE NVS read/write가 wrapper를 호출하는 것을 확인함.
  활성 프로필은 재부팅 전에 저장하되 런타임 주소/namespace는 부팅 전까지 바꾸지 않음.
  전환 중 신규 입력·등록을 차단하고 해제를 먼저 시도하며, 종료가 지연되면 최대
  6초 뒤 저장/재부팅함. 저장 오류 시 현재 프로필을 유지하고 재부팅하지 않음.
- **LED 수정:** HID Output 디스크립터의 LED usage와 비트 위치/report ID를 해석함.
  선택된 PC의 LED 상태를 비동기 SET_REPORT(Output)로 키보드에 전달하고 A/B 전환,
  USB 재연결 시 재반영함. 전송 중 데이터는 변경하지 않고 최신 상태를 대기시킴.
  다른 기능이 섞인 Output/지원하지 않는 형식은 임의로 쓰지 않으며, STALL 또는
  반복 출력 오류 시 해당 출력은 재연결 전까지 중단함. 제조사 전용 표시나 USB
  Output 리포트로 LED를 제공하지 않는 리시버는 지원이 제한될 수 있음.
- **검증:** 프로필 주소 유지·분리, namespace 선택, 재부팅 경계, 저장 실패,
  입력 해제 후 프로필 전환, 강제 종료 기한, A/B별 LED 상태 선택, LED report ID/
  padding/비트 배치, 전송 중 상태 변경·거부 응답을 호스트 테스트로 검증함.
  기존 입력/USB/BLE 회귀 테스트 및 ESP-IDF 6.1 ESP32-S3 빌드 통과.
  실제 Windows/Ubuntu 교대 부팅 및 키보드 표시 검증은 아직 필요하며 업로드하지 않음.

## OS 자동 구분 가능성 진단 명령

- **목적:** 동일 어댑터의 두 OS를 본딩 목록에서 자동 선택할 수 있는지 확인하기
  위해 COM `os inspect`를 추가함. 현재 프로필의 B 저장 identity, IRK 존재 여부와
  SHA-256 앞 16바이트 지문, Secure Connections 여부, 연결 중 identity/실제 연결
  주소와 RPA 여부를 출력함. LTK/IRK 원문은 출력하지 않으며 저장 정보는 변경하지 않음.
- **실행:** Ubuntu 프로필에서 노트북 Ubuntu를 B에 연결한 뒤 `status`, `os inspect`를
  실행하고, Windows 프로필에서 노트북 Windows를 B에 연결한 뒤 같은 명령을 실행함.
  아직 등록하지 않은 프로필은 `pair b`로 한 번 등록해야 함. 양쪽에서 재연결 후
  한 번 더 수집하면 식별 정보의 안정성도 비교할 수 있음.
- **판단:** 다른 peer identity는 직접 구분 후보, 다른 IRK와 실제 RPA 사용은
  IRK 기반 주소 해석 후보임. 같은 public/static 주소로 연결한다면 IRK 지문만
  다르다고 연결 전 자동 선택이 가능해지는 것은 아님. RPA 판별은 현재 연결 주소의
  형식 확인이며 향후 OS의 모든 연결 방식을 보장하지 않음. 현재 펌웨어는 아직
  자동 OS 선택을 하지 않음.
- **검증:** ESP32-S3 빌드, B만 대상으로 저장소를 읽고 프로필/등록을 변경하지 않는
  호스트 회귀 테스트 통과. 실기기 비교 결과와 SHA 지문 출력 확인은 대기 중.

## 새 B 페어링 시 PC 이름 조회

- **요청:** B 등록을 정리한 뒤 새 연결에서 OS 이름도 함께 확인.
- **수정:** B 연결 직후 Device Name(0x2A00)을 GATT로 조회함. 앱이 시작하는
  암호화 요청은 조회 완료/실패 또는 2초 경과까지 미루고, 이후 정상 인증을 진행함.
  PC가 먼저 암호화를 시작할 수도 있으므로 이름 로그에 encrypted_at_reply를 함께
  기록함. 조회 결과는 `os inspect`에도 표시되며 이름으로 인증하거나 프로필을
  자동 선택하지는 않음. 늦은 응답은 연결별 토큰으로 구분함.
  SDK의 GATT client 의존성에 맞춰 Central/GATT client 빌드 옵션을 활성화했지만
  보드가 PC를 스캔하거나 접속을 시작하는 동작은 추가하지 않음.
- **등록 정리 절차:** 해당 OS의 기존 보드 등록을 제거하고, 펌웨어 업로드 후
  대상 프로필을 선택해 COM에서 `forget b`, `pair b`를 순서대로 실행함.
  forget b는 현재 프로필의 B만 지우며 A와 다른 프로필의 B는 유지함.
  다른 프로필도 정리하려면 그 프로필로 전환한 뒤 같은 명령을 실행함.
  새 페어링의 연결 로그와 `status`, `os inspect`를 OS별로 수집함.
- **검증/상태:** 이름 응답, 늦은/중복 토큰, 2초 제한, 제출 실패 후 인증 진행을
  호스트 테스트로 확인함. 현재 작업 환경에 COM 장치가 노출되지 않아 실제 보드의
  등록 삭제와 업로드는 수행하지 못함. 실기기 이름 조회 가능 여부는 확인 대기 중.

## B 노트북 이름으로 OS 본딩 키 자동 선택

- 문제: 같은 공개 주소의 Windows/Ubuntu가 서로 다른 키를 사용해 암호화에 실패했습니다.
  실측 이름은 Windows `DESKTOP-36CBTO9`(끝 NUL이 과거 로그에서 `?`로 표시), Ubuntu `jsy`이며
  모두 `encrypted_at_reply=0`에서 읽혔습니다.
- 수정: 보드 전체 프로필 자동 전환 대신 B의 OUR_SEC/PEER_SEC 키를 OS별 NVS 레코드에
  저장하고 NimBLE 저장 콜백에서 선택합니다. A와 나머지 장치, 로컬 IRK, 보드 주소는 기존
  경로를 유지합니다. B의 기존 단일 키를 자동 추정·이관하지 않아 각 OS의 일회성 재등록이 필요합니다.
- 보호: 이름 미확인 시 기존 키 대체 사용 금지, 등록 창 밖 LTK 교체 금지, 현재 OS만 재등록,
  명시적 `forget b`/전체 초기화는 두 OS 레코드 삭제, NVS 오류 시 준비 완료로 처리하지 않습니다.
  인증이 이름 조회보다 먼저 완료되는 경우 연결을 거절하고 재접속하도록 로그를 남깁니다.
- 표시 이름: `ESP USB Switch`로 통일했습니다. 과거 OS명 기반 이름은 위 변경 이력에만 남깁니다.
- 검증: OS별 키 저장·재부팅 후 선택·알 수 없는 이름 차단·등록 창 밖 교체 차단·다른 OS 키 유지·
  A 저장 콜백 통과·삭제 실패 테스트와 기존 BLE 입력/해제 테스트를 실행했습니다.
  ESP-IDF v6.1 빌드도 통과했습니다. 실제 Windows↔Ubuntu 반복 전환은 하드웨어 검증이 필요합니다.

## B의 45ms 연결 간격과 rc=530 대체 요청

- 관측: A=15ms, B=45ms이며 B의 GAP/HCI 간격 단축 요청이 `rc=530`
  (`BLE_ERR_INV_HCI_CMD_PARMS`)으로 세 번 실패했습니다. 해당 USB 상태는 마우스의
  마지막 수신 5ms, 오류 0으로, 그 측정에서 USB 정지는 확인되지 않았습니다.
- 수정: 이미 7.5–15ms/latency=0인 연결에는 요청하지 않습니다. HCI 파라미터 오류가
  발생하면 2초 뒤 L2CAP Connection Parameter Update Request로 중앙 장치(PC)에
  7.5–15ms/latency=0/timeout=4s를 요청합니다. SDK는 LL 기능 미지원에는 자체 대체 경로가
  있지만 이번 HCI 파라미터 오류에는 자동 전환하지 않아 앱에서 처리합니다.
- 제한: 총 요청은 연결당 최대 세 번입니다. L2CAP 응답 실패 후에는 5초 대기합니다.
  오래된 콜백은 요청 토큰으로 무시합니다. 수락 응답은 실제 간격 변경과 같지 않으며,
  이후 `PC B BLE interval=...` 및 `status`로 확인해야 합니다. PC가 짧은 간격을
  허용하지 않으면 45ms가 유지될 수 있고, 양쪽 버벅임의 모든 원인을 해결했다는 뜻은 아닙니다.
- 검증: 15ms 연결 요청 생략, 530 대체 경로, 재시도 간격/횟수 제한, 오래된 콜백 무시,
  기존 GAP 성공 경로와 BLE 입력/해제 회귀 테스트 통과. 하드웨어 확인은 별도입니다.
- 적용: 빌드 후 업로드하고 B를 연결합니다. 페어링 정보 삭제는 필요 없습니다.
  `requested 7.5-15 ms via L2CAP: rc=0`은 요청 제출 성공이며 최종 간격을 확인하세요.

## 7.5ms 고정 간격 요청 시험

- 관측: 재접속 후 A/B가 모두 15ms로 연결됐고 사용자가 움직임이 부드러워졌음을 확인했습니다.
  더 짧은 간격을 시험하기 위해 요청 범위를 7.5–15ms에서 7.5ms로 변경합니다.
- 수정: GAP/HCI 및 L2CAP 모두 최소/최대 간격을 6(1.25ms 단위), latency=0,
  supervision timeout=4초로 요청합니다. 이미 7.5ms/latency=0일 때만 생략하고
  15ms 연결에서도 요청합니다. 기존 대체 경로와 연결당 최대 세 번 제한은 유지합니다.
- 검증: 두 요청 경로의 최소/최대 값, 15ms에서도 요청하는 동작, 7.5ms 생략,
  대체 요청 및 재시도 제한을 포함한 BLE 회귀 테스트 통과.
- 적용/판정: 업로드 후 재페어링 없이 연결하고 `status`의 실제 `BLE interval=7.50 ms`를
  확인합니다. 요청의 rc=0만으로 7.5ms가 적용됐다고 판단하지 않습니다. PC가 거절하거나
  다른 간격을 유지할 수 있으며, 실제 부드러움과 두 연결의 안정성은 하드웨어에서 확인합니다.
