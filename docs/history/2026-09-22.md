## 입력 적체와 USB 허브 후연결

- **보고된 문제:** 같은 키가 계속 눌리는 듯한 입력, 보드 전원을 먼저 켠 뒤
  허브를 연결하면 간헐적으로 키보드가 인식되지 않음.
- **확인한 코드 문제:** BLE 전송 실패 중 키보드의 중간 해제 상태가 최신 상태로
  덮어써질 수 있었음. USB 전송 오류 후 수신 재시작과 초기화 실패 재시도가 없었음.
- **수정:** 키 상태 변화의 순서를 보존하는 32개 대기열 추가, 250ms 이상 적체 폐기와
  중립 상태 전송, 입력 큐 손실 시 최신 USB 상태 복원 및 계속 누른 단축키 재실행 방지.
  USB 초기화 재시도, 오류 후 stop/start, 허브 안정화 대기와 입력 장치가 없는 경우
  루트 포트 재초기화를 추가함.
- **검증:** 빌드 및 파서·라우터·키보드/마우스 대기열·USB 복구 테스트 통과.
  적용 후 사용자의 초기 정상 동작 보고가 있었으나 장시간 무결함을 확인한 것은 아님.

## Espressif IDE 인식·Python·No binaries

- **보고된 문제:** 프로젝트 인식 실패, `/usr/bin/python`에서 `idf_component_manager`
  모듈을 찾지 못함, 실행 시 `No binaries` 발생.
- **확인한 설정 문제:** `test`가 일반 CMake 프로젝트로 등록되어 `Local` 타깃과
  PC용 실행 구성을 사용했음. ESP-IDF 전용 Python에는 필요한 모듈이 이미 있었음.
- **수정:** 로컬 `test/.project`를 ESP-IDF nature로 수정하고,
  `test/test-esp32s3.launch`에 `ESP-IDF Application` 실행 구성을 추가함.
  실제 프로젝트 루트는 `test/`이며 `test/main/`은 독립 프로젝트가 아님.
- **적용:** 프로젝트를 새로고침하고 `Run / test-esp32s3 / esp32s3` 및 해당 시리얼
  포트를 선택. `.project`는 Git에서 제외된 로컬 설정이므로 새 환경에서는
  `Import → Espressif → Existing IDF Project`로 `test/`를 가져와야 함.
  Build는 컴파일, ESP-IDF 구성의 Run/Launch는 보드 업로드에 사용함.

## 비선택 PC 절전 시 선택 PC 입력 정지

- **보고된 상황:** 양쪽 PC가 연결된 상태에서 **입력 대상이 아닌 PC**가 절전에
  들어가자 선택 PC로도 입력이 전달되지 않았고 전환 키도 효과가 없었음.
  허브를 재연결하고 절전 PC를 깨운 뒤 복구됨. 보드 COM/UART 전원은
  절전 PC가 아니라 **계속 켜져 있던 PC**에서 공급되었음.
- **확인·재현 1:** 어느 PC의 절전·복귀·구독 변경·암호화·연결 해제 이벤트든
  공통 라우터의 누른 키·버튼을 차단했음. 비선택 PC의 Suspend 이벤트로
  선택 PC의 유지 중인 키가 해제되는 것을 수정 전 호스트 테스트에서 재현함.
- **확인·재현 2:** PC 전환 후 이전 PC의 해제 전송이 실패하면 새 PC를 차단하고,
  3초 후 연결 종료를 요청하더라도 완료 이벤트까지 차단을 유지했음.
  종료 요청이 실패하는 상황에서 3초 후에도 차단되는 것을 테스트로 재현함.
  이는 전환/연결 정리의 추가 결함이며, 비선택 PC 절전 자체의 확정 원인은 아님.
- **수정:** 연결 상태 변화로 인한 누른 입력 차단은 해당 PC가 선택된 경우에만 적용.
  중복 Suspend/구독 이벤트는 무시. 종료 중인 연결은 입력 대상에서 제외하여
  다른 PC를 막지 않도록 하고, 종료 요청 반환값과 비동기 실패 이벤트를 처리함.
  실패 시 1초 간격 재시도, 이미 종료 중이면 중복 요청 억제, 이미 끊겼으면 상태 정리.
  공유 BLE 알림 버퍼는 선택 PC가 먼저 사용하도록 처리 순서를 변경함.
- **검증:** 수정 전 위 두 테스트의 실패를 확인한 뒤 수정 후 통과.
  비선택 PC 절전/복귀/분리, 선택 PC 절전 후 수동 전환, 늦은 분리 이벤트,
  재연결 후 중립 상태, 해제 시간 초과, 종료 요청 실패·진행 중·연결 없음,
  제한된 전송 버퍼에서 선택 PC 우선 처리도 테스트함. 펌웨어 빌드 및 기존 회귀 테스트 통과.
- **남은 확인:** 공통 키 차단은 키·버튼 유지 문제를 설명하지만, 보고된 마우스 이동까지
  포함한 전체 정지의 원인을 모두 확정한 것은 아님. 실기기 재현 당시 로그가 없어
  USB 전원/수신 상태와 BLE 무선·컨트롤러 정체는 추가 확인이 필요함.

## 허브 수신 정지·마지막 키 반복 재발

- **추가 보고:** PC 절전과 무관하게 입력과 전환 키가 모두 먹통이 되는 현상이 재발함.
  타이핑 중 발생하면 마지막 키가 반복되며, 두 경우 모두 허브를 뺐다 끼우면 복구됨.
  따라서 앞서 보고된 절전 시점만으로 BLE 절전이 전체 정지 원인이라고 볼 수 없음.
- **코드에서 확인한 결함:** USB HID 드라이버 1.2.1의 `in_xfer_done()`이 리포트를
  전달한 뒤 `usb_host_transfer_submit()`으로 다음 수신을 예약하면서 반환값을 무시함.
  예약 실패 시 오류 이벤트도 발생하지 않아 앱이 수신 중 상태로 남고,
  기존 오류 기반 stop/start와 입력 장치 없음 기반 루트 포트 복구가 작동하지 않음.
  키 해제 리포트를 놓치면 PC의 자동 반복으로 마지막 키가 계속 입력될 수 있음.
- **수정:** 재예약 실패를 `IN transfer resubmit failed: ...`로 기록하고
  `TRANSFER_ERROR`를 전달하도록 수정. 기존 앱 처리가 누른 입력을 해제하고,
  관리 태스크에서 endpoint stop/start를 재시도함. 관리 구성 요소를 직접 고치지 않고
  `test/components/usb_host_hid`에 원본 라이선스를 포함한 1.2.1 기반 소스를 두고
  manifest의 `override_path`로 지정해 클린 빌드에서도 수정이 유지되게 함.
- **검증:** 실제 드라이버 콜백을 컴파일해 재예약 성공/실패, 전송 오류, 취소,
  장치 분리의 이벤트와 재예약 횟수를 확인함. 기존 USB 복구·BLE 절전·입력 회귀
  테스트 및 ESP-IDF 6.1 / ESP32-S3 빌드 통과. LED 동작은 유지함.
- **한계:** 이 실패 경로의 결함은 확인했지만, 실제 멈춤 당시의 로그가 없어 이번
  증상의 확정 원인은 아님. 예약이 성공한 채 허브/호스트가 응답하지 않는 정체는
  이번 수정으로 감지하지 못함. 정상적인 무입력과 구분할 근거 없이 시간만으로
  USB를 재설정하거나 유지 중인 키를 해제하는 동작은 추가하지 않음.

재발 시 재부팅·허브 재연결 전에 가능하면 COM에서 `status`를 입력해 로그를 남깁니다.
이번 수정의 `IN transfer resubmit failed` 및 기존 `Transfer failed`/USB 복구 로그도
함께 확인합니다. 전환 키도 같은 USB 수신 경로를 쓰므로 수신 중단 시 작동할 수 없습니다.
`USB sources`는 인식된 입력 인터페이스, `reports`는 USB 입력 큐에 제출된 누적 리포트 수입니다.
키보드/마우스를 조작하면서 두 번 조회해 수신이 계속되는지 비교할 수 있습니다.
PC별 `suspended`, `keyboard_sub`, `mouse_sub`, `release`, `switch_release`,
`closing`, `terminate_pending`, `disconnect_failures`와 전체 `previous_release`로
절전·구독·해제 대기·연결 종료 상태를 구분합니다. `reports`가 증가해도 모든 입력이
PC에 전달됐다는 뜻은 아니며, `notify_failures`와 `stale_drops`도 함께 확인해야 합니다.

## 부팅 반복 로그에서 Brownout 확인

- **실제 로그:** BLE PHY 초기화 직후 `Brownout detector was triggered`가 발생하고
  ROM/부트로더부터 다시 시작하는 과정이 반복됨. 이는 USB 재시도 로그가 아니라
  저전압 감지에 따른 보드 전체 재부팅임. 해당 시점은 앱의 USB 호스트 초기화 이전임.
  PC가 계속 켜져 있어도 케이블·포트·보드 전원 회로의 전압 안정성까지 보장하지는 않음.
- **마지막 부팅:** PC A/B 모두 `ready`까지 진행했지만 USB `Detected`/`receiving`
  로그가 없고, 약 10.5초 간격의 `No usable USB input ... restarting root port`가
  나타남. 빨간 RGB 상태 LED는 인식된 USB 입력 소스 없음과 일치함.
  이 USB 인식 실패까지 Brownout과 같은 원인인지는 아직 확인되지 않음.
- **다른 로그:** PC B의 `rc=530 / Invalid HCI Command Parameters`는 BLE 연결
  간격 변경 요청 실패이며 코드상 최대 3회 시도함. PC B는 이미 ready에 도달했으며
  이 메시지는 보드 재부팅 또는 USB 초기화 메시지가 아님. 16MB 실물 플래시와
  2MB 이미지 설정 차이 경고도 별도 설정 사항이며 Brownout의 근거가 아님.
- **조치/확인 순서:** 허브를 분리하고 COM 전원만으로 부팅 안정성을 확인한 뒤,
  전원용 USB 케이블과 PC의 직접 연결 포트를 하나씩 바꿔 비교함. 안정적으로
  부팅되면 빈 허브, 키보드, 마우스 순서로 연결하여 재부팅/인식 로그를 비교함.
  허브 자체 전원 사용 여부와 실제 보드의 USB VBUS 공급 방식도 확인이 필요함.
  Brownout 감지를 끄거나 임계값을 낮추는 변경은 하지 않음.
- **상태:** 이번에는 로그 진단과 기록만 수행. 전원 경로별 실기기 비교는 아직
  수행하지 않았으며, 이전 사용 중 입력 정지까지 모두 전원 문제로 확정하지 않음.

## 장시간 사용 후 notify 로그 중단 보고

- **추가 관찰:** 별도 전원을 쓰는 허브를 사용 중이며, 일시적으로 정상 동작한 뒤
  부팅 후 약 103분 시점에 `GATT procedure initiated: notify; att_handle=26`
  로그가 이어지다 멈췄다고 보고됨. 초록색 LED는 계속 점멸함. 제공된 구간에는
  Brownout, 재부팅, USB 전송 오류 로그가 없음.
- **해석:** notify는 BLE 알림 전송 시도 로그이며 수신 PC의 처리 완료를 뜻하지 않음.
  LED는 별도 태스크가 마지막 전달받은 상태로 계속 점멸하므로 USB 수신이나 BLE
  처리 태스크가 정상 진행한다는 증거가 아님. 입력이 없으면 notify도 멈출 수 있어
  로그 중단만으로 정지 위치를 확정하지 않음.
- **다음 진단:** 허브 재연결 전에 COM `status` 응답 여부를 확인하고 실제 입력을
  발생시킨 전후의 `reports`, `queue`, `notify_failures`, 대기열 상태를 비교함.
  status 명령도 BLE 처리 큐를 거치므로 무응답만으로 보드 전체 정지를 단정하지 않음.
  이 보고에 대해 추가 펌웨어 변경은 아직 하지 않음.

## 입력 조작 전후 reports 정지 확인 및 수동 USB 복구 추가

- **실제 비교:** 두 status 사이 약 55초 동안 마우스 이동/클릭을 했지만
  `reports=101014`, `sources=0x7`, `queue=0`이 유지됨. BLE 명령은 응답하고,
  양쪽 PC는 ready이며 대기 입력도 없음. 새로운 해석된 USB 입력이 앱에 전달되지
  않는 것으로 범위가 좁혀짐. 다만 기존 카운터만으로 수신 콜백 정지와 리포트
  읽기/해석 실패를 구분할 수는 없음.
- **별도 BLE 이벤트:** 중간에 PC A가 reason=520(0x208, 연결 감시 시간 초과)으로
  끊겼다가 약 0.7초 뒤 ready로 복귀함. 이후에도 reports는 그대로임. A의
  notify_failures가 129에서 0이 된 것은 연결 컨텍스트가 재생성됐기 때문이며,
  USB 복구의 근거가 아님. 광고 rc=6 및 간격 변경 rc=530은 별도로 관찰됨.
- **수정:** `usb status`에 인터페이스별 수신/해석/오류 카운터를 추가하고,
  `usb reset`으로 수신 중으로 표시된 인터페이스도 수동 재인식할 수 있게 함.
  console은 요청만 전달하고 실제 진단·재설정은 USB 관리 태스크에서 수행함.
  리셋 중 이전 핸들 재시작과 늦은 입력 전달을 차단하고, 분리 후 재연결로 정리함.
- **검증:** USB 호스트 테스트에서 수신/해석 실패 구분, 진단의 비파괴성,
  수동 재설정 실패·성공·중복 요청, 재설정 중 늦은 입력 차단 및 재연결 시
  카운터 초기화를 확인함. ESP-IDF 6.1 / ESP32-S3 빌드 통과.
  아직 새 펌웨어를 업로드하거나 실제 허브 정지 상태에서 복구 효과를 확인하지 않음.

## 허브 재연결 후 제어 전송 실패와 재분리 로그

- **관찰:** 물리적 허브 재연결 후 외부 허브 addr=4의 포트 제어 요청이
  `Control request bad transfer status 7`로 실패함. 현재 USB 스택에서 7은
  `USB_TRANSFER_STATUS_NO_DEVICE`(전송 대상 장치 소실)이며, 전압 측정 결과가 아님.
  허브 드라이버는 오류 상태로 들어가 제거를 기다림. 이후 앱의 루트 포트 복구로
  Apple 키보드 및 Logitech 키보드/마우스 인터페이스가 receiving까지 도달함.
- **두 번째 분리 — 사용자 확인:** 재연결 후 마우스를 움직여 정상 동작을 확인한 뒤,
  로그 출력을 멈추려고 사용자가 허브를 다시 분리함. 따라서 약 7초 뒤 addr=7/8의
  인터페이스 3개가 모두 분리된 것은 자발적 장애가 아니며, 이후 약 10.5초 간격의
  루트 포트 복구 반복도 허브가 없는 상태의 기존 동작임. 물리적 재연결로 입력이
  복구된 것은 확인됐지만, 이전 수신 정지의 원인이 밝혀진 것은 아님.
- **구분:** `EP command error: ESP_ERR_INVALID_STATE`는 분리 시 endpoint 정리
  과정에서도 발생할 수 있어 최초 원인으로 단정하지 않음. Apple 장치의 보조 mouse
  인터페이스는 descriptor 미지원으로 닫혔지만, 그 뒤 실제 Logitech 마우스는
  receiving에 도달했으므로 전체 장치 재분리와 구분함. 이 구간에도 Brownout이나
  보드 재부팅 기록은 없으며, 전원/접촉/허브/호스트 소프트웨어 중 원인은 미확정임.

## 입력마다 반복되는 로그 억제

- **문제:** 마우스 입력마다 NimBLE의 `GATT procedure initiated: notify`와
  `att_handle` 로그가 쌓여 장애 직전의 연결·오류 로그를 찾기 어려웠음.
- **수정:** NimBLE 로그 수준을 Warning으로 변경해 Info 수준의 전송 로그를
  제외함. 현재 `test/sdkconfig`와 새 환경용 `sdkconfig.defaults` 모두 반영함.
  원시 키보드/마우스 출력 옵션 `CONFIG_INPUT_SWITCH_LOG_INPUT`은 기존처럼 비활성화.
  NimBLE 경고·오류, 앱의 연결/분리·복구 로그, `status` 및 `usb status`는 유지함.
- **기존 환경:** defaults는 기존 sdkconfig를 덮어쓰지 않으므로 필요하면
  menuconfig에서 `NimBLE Host log verbosity`를 `Warning logs`로 선택함.
  이 변경은 로그 양을 줄이는 것이며 USB 정지의 원인 해결을 의미하지 않음.
