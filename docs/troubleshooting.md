# 진단과 복구

[사용 안내](../README.md) · [수정 일지](history/README.md)

명령과 빌드 예시는 저장소 최상위에서 실행합니다.

## 증상별 시작점

| 증상 | 먼저 확인할 내용 |
| --- | --- |
| 입력이 멈추거나 키가 반복됨 | `status`, `usb status`를 저장한 뒤 필요하면 `usb reset` |
| B의 OS 변경 후 인증 실패 | `trying saved ... key`, 인증 실패 이유, 다음 재접속의 후보 키 확인 |
| 두 저장 키의 시도가 중단됨 | `os retry`로 실패 기록만 초기화하고 B 재접속; `forget b`는 키까지 삭제 |
| 마우스가 버벅임 | `status`의 실제 BLE interval과 전송 실패·대기열 확인 |
| 부팅 로그가 계속 반복됨 | `Brownout detector was triggered` 등 리셋 원인 확인; USB 재시작 로그와 구분 |

`last_callback_ms`가 크다는 사실만으로 USB 장애라고 판단하지 않습니다. 마우스를 멈춘 동안은
값이 커지는 것이 정상입니다. `status`는 순간 상태이므로 증상 전후 로그도 함께 확인합니다.

## 마우스 지연 진단

USB 입력은 BLE 호스트에 이벤트를 보내 즉시 처리하며, 10ms 타이머는 유지 관리와
전송 재시도에 사용합니다. 암호화된 연결에는 7.5ms 고정 연결 간격과 latency 0을
요청합니다. 실제 적용값은 PC가 결정하며 연결 로그와 `status`에서 확인할 수 있습니다.

BLE 알림 전송이 일시적으로 실패하면 마우스 이동량을 보관해 재시도합니다.
같은 버튼 상태의 이동량은 합산하고, 버튼 상태가 바뀌는 순서는 유지합니다.
키보드는 최대 32개의 상태 변화를 순서대로 보관하므로, 전송 실패 중에도
`누름 → 뗌 → 다시 누름`의 중간 해제가 덮어써지지 않습니다.
보관 큐가 가득 차거나 전송 적체가 250ms 이상 지속되면 이전 입력을 폐기하고
키·버튼을 해제합니다. USB→BLE 입력 큐에서도 250ms 이상 된 입력은 재생하지 않습니다.
과부하 복구 시 USB 입력의 최신 상태를 반영하며, 계속 누르고 있던 키는
한 번 뗀 뒤 다시 눌러야 전달됩니다. PC 전환 시에도 이전 대기 입력은 지웁니다.
해제 알림조차 3초 동안 보내지 못하면 해당 BLE 연결을 종료해 재연결하게 합니다.
정상적으로 길게 누르는 키에는 유지 시간 제한을 적용하지 않습니다.

`status`의 `pending_mouse`, `pending_keys`는 대기량,
`notify_failures`, `mouse_overflows`, `key_overflows`는 연결별 누적 실패 횟수,
`stale_drops`는 BLE 전송 적체를 시간 제한으로 폐기한 횟수입니다.
USB→BLE 입력 큐의 시간 초과·포화는 별도 로그로 확인합니다.

## USB 허브 후연결·수신 오류 복구

HID 드라이버 준비가 끝난 뒤 USB 루트 포트를 켭니다. 허브 하위 포트의 전원 안정화
대기 시간은 500ms, 리셋 복구 시간은 100ms로 설정합니다. HID 인터페이스를 발견한 뒤
250ms를 기다리고 초기화하며, 프로토콜 설정·디스크립터 요청·수신 시작이 실패하면
250ms 간격으로 재시도하고 반복 실패 시 2초 간격으로 늦춥니다.

USB 전송 오류는 키·버튼을 해제한 뒤 `stop → start`로 수신을 재개합니다.
키보드에는 SET_IDLE로 100ms 간격의 현재 상태 보고를 요청해 일시적으로 놓친
해제를 보정합니다. 이를 무시하거나 지원하지 않는 리시버도 있으므로,
일정 시간 입력이 없다는 이유만으로 정상적인 키 누름을 해제하지는 않습니다.
분리 콜백에서는 소스 재사용과 핸들 정리를 담당 작업으로 넘겨 초기화와의 충돌을 줄입니다.

동작 중인 키보드·마우스 인터페이스가 10초 동안 하나도 없으면 루트 포트를
500ms 동안 끈 뒤 다시 켜서 HID 연결 이벤트 이전의 인식 실패도 재시도합니다.
입력 장치가 없는 동안에는 이 복구를 반복합니다. 하나라도 동작 중이면 전체 허브를
재시작하지 않습니다. 이는 USB 포트 재초기화이며 외부 전원 허브의 실제 전원 차단은 아닙니다.

기존 `test/sdkconfig`가 있으면 `sdkconfig.defaults`의 새 값이 자동으로 덮어써지지
않을 수 있습니다. `idf.py -C test menuconfig`의 `Component config → USB-OTG →
Hub Driver Configuration`에서 다음 값을 확인하세요.

- Root Port: Reset recovery delay = 100ms
- Downstream Port: Reset recovery delay = 100ms
- Downstream Port: Custom bPwrOn2PwrGood value = 활성화, delay = 500ms

진단 로그는 `USB retry`, `transfer error`, `receiving`,
`No usable USB input ... restarting root port`로 구분됩니다.

COM의 `usb status`는 BLE 큐를 거치지 않고 USB 관리 태스크에 진단을 요청합니다.
인터페이스별 `callbacks`(수신 콜백), `decoded`(해석 후 전달), `read_errors`,
`decode_errors`, `transfer_errors`, `last_callback_ms`(마지막 콜백 이후 시간)를
출력합니다. 카운터는 해당 인터페이스가 새로 연결되면 초기화됩니다.
`Queued usb status`만 나오고 진단이 나오지 않으면 USB 관리 태스크의 진행 여부도
확인해야 합니다. 이 명령은 기존 BLE `status`와 함께 사용합니다.

입력이 실제로 멈춘 경우 먼저 `usb status`를 저장한 뒤 `usb reset`으로 USB 루트
포트를 500ms 동안 비활성화했다 다시 활성화할 수 있습니다. 성공적으로 재설정을
시작하면 기존 입력을 차단하고 키·버튼 해제를 요청하며, 분리 콜백을 기다려 이전
핸들을 정리합니다. BLE 페어링 정보는 유지됩니다. 별도 전원 허브의 실제 전원을
껐다 켜는 동작은 아니므로 물리적 재연결과 같은 복구 효과를 보장하지는 않습니다.
정상적인 무입력 상태를 장애로 오인하지 않도록 무입력 시간만으로 리셋하지 않습니다.

USB 상태 감시는 수신 중인 HID 장치를 주소별로 감시합니다. 같은 리시버의 키보드와
마우스는 한 장치로 묶으며, 최근 1초 구간에 리포트 8개 이상을 받은 경우 이후
3초 동안, 또는 키·버튼이 눌린 상태에서는 0.5초간 콜백이 없으면 검사합니다.
그 외에는 5초 무입력 후 표준 장치 `GET_STATUS` 요청을
비동기로 보냅니다. 정상 완료 또는 STALL(요청 거부 응답)이면 응답 가능한 장치로
판단해 입력을 해제하거나 리셋하지 않습니다. 계속 조용하면 1초 간격으로 확인합니다.
완료된 전송 오류가 3회 이어지거나, 제출된 요청이 0.5초 뒤에도 완료되지 않고 1초
간격의 추가 확인 2회에서도 완료되지 않으면 `Automatic USB root restart`로
복구합니다. 새 입력 또는 정상/거부 응답은 실패 횟수를 초기화합니다.
자동 복구 요청/USB 재설정 후 60초간은 새 상태 요청과 자동 복구를 쉬며,
`usb reset` 수동 명령은 계속 사용할 수 있습니다.

`usb status`에는 `usb_health`의 주소별 `probes`, `replies`, `stalls`, `failures`,
`pending`, `gone`도 출력됩니다. 제출 자체의 로컬 오류는 로그만 남기며 자동 리셋의
근거로 삼지 않습니다. 제어 응답은 정상인데 인터럽트 입력만 멈추는 경우는 정상
무입력과 아직 구분할 수 없으므로 자동 수신 재시작을 하지 않습니다. 이때는 진단을
저장하고 수동 `usb reset`으로 복구해야 합니다. 상태 감시는 BLE와 독립적이며,
보드 전체 또는 USB 관리 태스크가 멈추는 경우까지 복구하는 watchdog은 아닙니다.
